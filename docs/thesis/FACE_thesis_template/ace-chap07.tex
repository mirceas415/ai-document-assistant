\chapter{Testing and Evaluation}
\label{chap:testing-evaluation}

Testing and experimental evaluation answer different questions. Automated tests determine whether specified implementation behavior is preserved: for example, whether an unauthorized project is rejected, a chunk stays below its hard token limit, or invalid reranker identifiers trigger the documented fallback. Experimental evaluation asks how well the complete system performs on representative documents and questions. Passing orchestration tests does not establish retrieval accuracy, OCR quality, or answer correctness. This chapter therefore reports the verified automated suite separately from a methodology and empty result structure for the final evaluation.

\section{Automated Testing Strategy}
\label{sec:automated-testing}

The backend test project uses xUnit with controlled substitutes at external model boundaries and, where appropriate, Entity Framework Core's in-memory provider. Generated PDF and DOCX fixtures make extraction tests reproducible without private documents. Deterministic fake embedding, reranking, understanding, and answer services allow tests to control model responses without sending document content or consuming provider resources. SQL-shape tests complement in-memory service tests where PostgreSQL-specific vector and full-text behavior matters. This layered strategy follows established distinctions among unit, integration, and system-level testing \cite{Ammann2016SoftwareTesting}.

On 4 September 2026, the complete solution test command was executed once from the repository root:

\begin{center}
\texttt{dotnet test AI.DocumentAssistant.slnx --verbosity minimal}
\end{center}

The run discovered and passed 345 tests, with zero failures and zero skipped tests. The reported execution duration for the test assembly was approximately two seconds, excluding restore and build time. Static inspection also found no skipped test attributes. These numbers describe the current backend test suite; the React client does not presently have an automated test script or frontend test files.

Tests around model-dependent stages focus on contracts and local authority. For Document Understanding, they provide malformed categories, invalid confidences, duplicate metadata, oversized fields, adversarial document instructions, and changed source hashes. For reranking, they control the candidate identifiers and relevance grades and verify both accepted partial orderings and rejected output. For answering, they supply valid and invented \texttt{S}-identifiers and confirm that only mappings created from the selected context become structured sources.

The suite also exercises failure isolation. A failed technical analysis must not prevent native extraction. A failed Document Understanding request must not prevent chunks and embeddings from making the document retrievable. An OCR failure may coexist with successful ingestion only when another page still provides useful text. If embedding generation fails before initial persistence, incomplete new chunks must not replace the prior authoritative state. These cases validate the lifecycle described in Section~\ref{sec:ingestion-status-isolation}.

Automated success has limits. Provider substitutes cannot measure live model relevance, recognition quality, network latency, or cost. The in-memory database cannot execute PostgreSQL's cosine and full-text operators. Query-text assertions verify important filters, but the final evaluation must still run against the intended PostgreSQL configuration. Likewise, the absence of frontend automation means that the screenshot and manual interaction pass must verify the visible behavior described in Chapter~\ref{chap:application-ux}.

\section{Evaluation Methodology}
\label{sec:evaluation-methodology}

The final evaluation will use the separately prepared synthetic corpus. No quantitative evaluation has yet been performed for this first draft. The method below is designed to make future measurements repeatable and to prevent attractive examples from being presented as a benchmark.

\subsection{Controlled setup and ground truth}

Before running cases, the evaluator should record the repository revision, database version, model identifiers, tokenizer, chunking parameters, candidate limits, RRF configuration, reranking configuration, OCR languages and rendering limits, and time of execution. The same ingested documents and current embeddings must be used when retrieval variants are compared. A configuration change requires a new recorded run rather than silently replacing an earlier result.

Each synthetic document should have a manifest that identifies its intended document type, primary language, title/subject expectations, controlled metadata values, technical page types, exact source text, and the questions it is designed to answer. Retrieval questions should identify all acceptable relevant chunks before results are viewed. Security cases should contain fictional canary strings and no real credential. This produces a ground truth independent of the application's prediction.

The corpus should cover at least:

\begin{itemize}
    \item born-digital PDF, scanned PDF, mixed PDF, image-based page, blank/unknown page, and structured DOCX;
    \item Romanian, English, and mixed-language content with Romanian diacritics and additional Unicode characters;
    \item paraphrased questions, exact identifiers, organization names, dates, monetary values, and exact phrases;
    \item similar documents that require a type or metadata distinction;
    \item questions with one known supporting chunk, questions with several acceptable chunks, and questions for which the collection contains no answer; and
    \item benign facts placed near adversarial instructions that attempt to redirect understanding, reranking, or answer generation.
\end{itemize}

Project and user isolation should be part of the setup, not a separate informal check. A distinctive term can be repeated in a second workspace and another user's workspace with different facts. Neither source may appear in the evaluated workspace's results, model context, answer, citation, or diagnostics.

\subsection{Document Understanding evaluation}

For every document, compare the stored controlled type and primary language with the manifest. Type and language are exact-match classification tasks. Optional subtype, title, and subject require a written rubric because several phrasings can be acceptable. Metadata entries should be matched by kind and normalized value where normalization is defined; person and organization spelling should be compared conservatively without inventing aliases after seeing the prediction.

Report accuracy for controlled type and language. For metadata, report precision and recall over labelled entries: precision measures the fraction of returned entries that are correct, while recall measures the fraction of expected entries that were returned. Title and subject can be scored as correct, partially correct, or incorrect by a reviewer, with the rubric recorded before scoring. Understanding marked \texttt{Skipped} or \texttt{Failed} must be counted explicitly rather than removed from the denominator.

The representative-sampling path needs at least one document exceeding the 6,000-token input bound. Expected fields should be distributed across the beginning, middle, and end, while another expected value can be placed outside the selected sample. The latter case helps distinguish a designed sampling limit from a validation defect. Repeating the same build checks determinism and idempotent reuse, not semantic quality.

\subsection{Technical PDF and OCR evaluation}

Technical classification should be evaluated at page level and document level. The corpus manifest assigns one of \texttt{TextBased}, \texttt{Scanned}, \texttt{ImageBased}, \texttt{Mixed}, or \texttt{Unknown} to each page using independently inspected construction facts. Compare these labels with stored diagnostics and create a confusion matrix. Boundary fixtures should separately exercise 40 alphanumeric characters, eight useful words, 0.30 substantial image coverage, 0.80 page-sized coverage, the 80\% document majority, and the allowed unknown-page count.

OCR evaluation has two components. \emph{Routing correctness} asks whether every intended scanned page was selected and every non-scanned page avoided unnecessary OCR. \emph{Content recovery} compares recognized text with a known transcription. Character Error Rate or a carefully defined exact-field score can be used, provided the chosen metric and normalization are fixed before the run \cite{OCRDEvaluation}.

The OCR record must also be checked for correct page order, source type, requested/effective DPI, pixel limit, status, recognition count, and \texttt{UsedInExtraction}. A mixed PDF should demonstrate that native pages remain native while selected scanned pages receive OCR provenance. Very poor or empty scans should be retained as failed/empty observations rather than discarded.

\subsection{Retrieval comparison}

Every labelled question will be evaluated under three variants:

\begin{enumerate}
    \item \textbf{Vector-only baseline}: order eligible chunks only by pgvector cosine distance.
    \item \textbf{Hybrid retrieval}: combine semantic, lexical, and applicable metadata ranks through the implemented weighted RRF, without applying the model reranker.
    \item \textbf{Hybrid + reranking}: use the same hybrid candidate generation and allow the bounded reranker to produce the final order.
\end{enumerate}

The comparison must keep the workspace, question text, chunks, embeddings, and TopK fixed. For the reranked variant, record whether reranking was actually applied. A timeout or unavailable provider is a successful availability fallback but is not evidence for or against ranking quality. Record vector, lexical, metadata, hybrid, rerank, and final positions through the advanced diagnostics so that individual changes can be explained after aggregate metrics are calculated.

Query groups should be reported separately as well as together: semantic paraphrase, exact identifier, exact phrase/name, date/amount, document-type distinction, Romanian, English, and mixed Unicode. This prevents an overall average from hiding a regression in a practically important category. No weight or prompt should be tuned on the final test questions; if tuning becomes necessary, split the corpus into development and held-out evaluation sets.

\subsection{Answers, citations, no-evidence, and security}

After retrieval measurement, issue the corresponding question through the full conversational path. A reviewer should compare each factual statement with the source chunks returned by the backend. An answer is correct only when it addresses the question and its factual content is supported by the collection. Fluent but unsupported additions count against correctness.

Citation evaluation has two levels. Mapping correctness confirms that the displayed identifier belongs to the source object returned by the backend and that its excerpt and provenance match the stored chunk. Support correctness asks whether that chunk actually supports the associated statement. The former is strongly constrained by implementation and tests; the latter still needs human or separately verified judgement.

No-evidence questions should include an empty eligible collection and an unrelated question asked of a non-empty collection. The first should bypass answer generation and return the fixed no-information response. The second tests whether the answer model declines despite receiving weak nearest neighbours. Security cases should place instruction-like text in a document, retrieve it when relevant, and verify that understanding, reranking, and answering treat it as data. The evaluator must never place a real API key in the corpus or inspect a real secret to determine whether the test passed.

\section{Evaluation Metrics}
\label{sec:evaluation-metrics}

Let $Q$ be the set of evaluated questions. For a question $q$, let $R_q$ be the set of chunks labelled relevant before execution, and let $L_{q,k}$ be the first $k$ returned chunks.

Top-1 accuracy is

\begin{equation}
    \operatorname{Top1} = \frac{1}{|Q|}
    \sum_{q\in Q}\mathbb{I}\!\left[L_{q,1}\cap R_q\neq\emptyset\right],
    \label{eq:top1-accuracy}
\end{equation}

where $\mathbb{I}$ equals one when the first result is relevant and zero otherwise. Top-$k$ recall is

\begin{equation}
    \operatorname{Recall@}k = \frac{1}{|Q|}
    \sum_{q\in Q}\frac{|L_{q,k}\cap R_q|}{|R_q|}.
    \label{eq:recall-at-k}
\end{equation}

The final report will use $k=3$ and $k=8$. If every question has exactly one labelled relevant chunk, Recall@3 and Recall@8 reduce to the fraction of questions for which that chunk appears within the first three or eight results. When several chunks are acceptable, Equation~\ref{eq:recall-at-k} gives partial credit for retrieving some but not all of them \cite{Manning2008IR}.

\section{Discussion Framework}
\label{sec:discussion-framework}

The discussion will be completed only after the result tables and plots contain verified observations. It should explain error patterns rather than repeat percentages. The following prompts define the intended analysis:

\begin{itemize}
    \item \todocomplete{After evaluation, discuss cases where hybrid retrieval changed exact-identifier, phrase, date, amount, or organization-name results relative to the vector baseline.}
    \item \todocomplete{Determine whether reranking promoted relevant semantic evidence, preserved clear exact matches, or introduced regressions; report fallback runs separately.}
    \item \todocomplete{Relate false PDF classifications to the meaningful-text and image-coverage heuristics, including borderline and mixed pages.}
    \item \todocomplete{Separate OCR routing errors from recognition errors and identify scan properties associated with each.}
    \item \todocomplete{Analyze Document Understanding errors by controlled type, language, sampled document region, and metadata kind.}
    \item \todocomplete{Review every incorrect or partially correct answer for retrieval failure, context truncation, model interpretation, citation support, or missing source evidence.}
    \item \todocomplete{Report prompt-injection and no-evidence cases conservatively; do not generalize a finite pass set into a claim of complete security.}
    \item \todocomplete{Record latency and provider-use trade-offs for reranking and compare them with any measured quality difference.}
\end{itemize}

Threats to validity must also be addressed. A small synthetic corpus may not represent long, noisy, or domain-specific real collections. Carefully constructed identifiers can make exact retrieval easier than uncontrolled data. Model services may vary across time even when a model identifier is unchanged. Human scoring of title quality, answer correctness, and citation support can be subjective; a written rubric and, if possible, a second reviewer reduce this risk. Tests on a local demonstration database do not establish throughput at production scale.

The final discussion should conclude with what the measurements support, not what the architecture was intended to achieve. Until those measurements exist, this chapter establishes verified implementation testing and a reproducible evaluation plan, while all quality result cells remain explicitly pending.
